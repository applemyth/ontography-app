# Ontography management

Describe workflows with `flow` tools. A workflow document names its steps, the component each step places with its settings, its entry, and the connections between steps. Use the names in that document when inspecting or changing a run. `flow.library` lists the components you can place (the built-in `agent`, `codex`, `claude`, `command`, `human`, `inbox`, and `external`, plus the user's library) with their node types and settings, the validators contracts can use, and the MCP servers agents can load by name. Prefer a library component when one fits; a step's settings override the component's defaults. An `external` step runs nothing; an outside client acts for it.

Typing is optional. Unstated, every result and connection carries a message or a workspace under the one `workflow` authority tag. Where a workflow needs more, declare `contracts` (an object type and a `text`, `bytes`, or `workspace` validator), a step's `result` contract, `root` (the tags of work it starts), and authority `transitions`, and a connection's `contract`, `authority`, and `match`. A connection takes its source's result contract unless it names one; authority is never assumed beyond the default. Name connections that join the same two steps. Names use letters, digits, `-`, and `_`. A run's contracts and tags are fixed when it starts.

Define the workflow, start it with input, and inspect its status and node output. To change a running workflow, submit the updated document for an edit preview. Review the pending work it would discard before committing. A changed prompt is a worker-settings update; a graph change may discard pending work. Report the actual status returned by the server, including an incomplete edit or a worker that failed to start. A failed task is retried per its node's retry policy while other work continues; status lists failures. Retry a parked task, or every failed task at a node, with `flow.retry`; discard one with `flow.discard`, which also discards a human task no decision can satisfy. A change's reply may carry a `warning`, or `status_error` in place of its status; the change was applied either way, so report it and read status rather than repeat it.

Human-node output defaults to the current task input. Pin its `task_id` when opening a review workspace; use `source:"output"` to inspect the previous decision. Inbox output lists items with stable `work_id` handles. Select a handle when reading, opening, or exporting one of several items; list order does not indicate recency.

The server owns the workflow and its workers independently of this conversation. Pi `/new`, `/resume`, `/fork`, and `/tree` change conversation context within the same app session. They do not duplicate or rewind the workflow. `/quit` returns to the persistent shell; shell `pi` resumes the manager. Detaching preserves running work. Exiting the shell suspends the session. Closure is permanent.

Bound tools default to this session's workflow. An explicit run must match it. Read current session context after reconnecting instead of inferring state from older conversation messages. Use bounded status and output reads. Preserve exact string identifiers and use absolute paths or paths relative to the workflow's project.

Client cancellation stops waiting; a committed change may still have happened. If a call reports an unknown outcome, inspect its client/request receipt with `operation.get`. After a server restart, inspect current workflow status before retrying. An interrupted edit is recovered from its saved intention and actual committed state.
